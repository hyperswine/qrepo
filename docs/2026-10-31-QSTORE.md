# qstore: large blobs, stored and sent efficiently (proposal)

**Status: proposal, 2026-10-31.** Nothing here is built yet.

qstore is the part of qrepo that decides how objects sit on disk and travel
between devices. Today that is one rule: every object is a file
`.qrepo/objects/<sha256>` holding `kind + "\n" + body`, and a transfer
carries objects whole. qstore keeps that rule for small objects and adds
chunked, compressed representations for large ones. History does not change:
commits, trees and blob ids keep the meaning and the hashes they have today.

## Why

Measured on 2026-10-31 (macm4, a 512 MiB random file, through a local
server):

| | today |
|---|---|
| commit | 1.0 s, 3 MiB peak memory |
| `status`, nothing changed | 0.3 s: every file is hashed again |
| one byte changed, then committed | the store grows by **512 MiB** |
| push of both versions | 7.0 s, 1 GiB sent |

Memory is already flat, since bytes stream through `posix.c` 64 KiB at a
time. The cost is elsewhere:
- **No deltas:** every version of a file is stored and sent whole.
- **No compression:** notes, CSV and JSON take 3 to 5 times the space they
  need.
- **No cache:** every `status`, which the VS Code extension runs every 60 s,
  hashes every file again.
- **No resume:** an interrupted push of a large file starts over.

## Goals

1. **Store and send what changed, not whole files.** A small edit to a large
   file costs about one chunk, not the file.
2. **Compress what compresses, and leave alone what doesn't.**
3. **Keep content addressing and immutability.** Every stored byte is checked
   against a SHA-256 whenever it is read; nothing is rewritten in place; a
   name means one thing forever.
4. **Keep identities stable.** A file's id is the hash of its bytes, whatever
   way it is stored, so ids in history never change, and a store can be
   re-encoded without touching history.
5. **Keep memory flat and every step streaming,** as today.
6. **Make large transfers resumable,** and keep the one-request-at-a-time
   server responsive.
7. **Adopt it gradually.** Format 2 repositories and protocol-3 clients keep
   working.

Not goals, for now: encryption at rest; partial checkout (only some files
on a device); per-device quotas; format-aware chunking inside ZIP-based
documents (see Phase 4).

## The central idea: logical identity, physical representation

Two layers, kept apart.

**Logical objects** are what history refers to: `blob`, `tree`, `commit`,
with identity `SHA-256(kind + "\n" + body)`, exactly as in format 2. A tree
entry names a blob id; a blob id is the hash of the file's bytes with its
`blob\n` prefix. This layer does not change at all.

**Physical representations** are how a logical object's bytes are stored and
sent. An object has exactly one id and may be stored in one of these forms:

- **whole**: `.qrepo/objects/<id>`, as today (`kind\nbody`, uncompressed).
- **chunked**: a *layout* that lists *chunks*, each stored compressed or raw,
  whose concatenation is the object's body.

Reading an object always ends in the same check: the bytes produced must hash
to the id that was asked for. So a representation can be wrong, from a bug,
a bad disk or a lying server, but never silently. Changing a representation
(compressing at a higher level, converting whole to chunked, repacking) never
changes an id, so history, merges, blame and verified marks are unaffected.

This is what keeps the system easy to address: you always ask for content by
the hash of its bytes. And it is what keeps it hard to corrupt: everything
read is checked against that hash, at every layer.

## Chunks

A **chunk** is a run of a large blob's bytes.

- **Identity:** `chunk-id = SHA-256("chunk\n" + raw bytes)`. It is the hash of
  the uncompressed bytes, so the same bytes have one id however they are
  compressed, and dedup works across files, versions and devices.
- **Where:** `.qrepo/chunks/<first two hex>/<chunk-id>`, sharded so no
  directory holds hundreds of thousands of files.
- **File format:** a fixed header, then the payload.

      "qchk1"            5 bytes, magic and version
      encoding           1 byte: 0 raw, 1 zstd, 2 zstd with dictionary
                         (later: 3 delta, see Phase 4)
      dictionary id      32 bytes, zero unless encoding 2
      raw length         8 bytes, big-endian
      payload            the stored bytes

- **Reading:** decode into a buffer of exactly `raw length` bytes, refusing
  more output (no decompression bombs), hash, and compare with the file's
  name. A mismatch is corruption, reported with the chunk id; the chunk is
  never used.
- **Writing:** the same as today's objects: a temporary file in the same
  directory, `fsync`, exclusive publication (an existing chunk is compared,
  not overwritten), then a directory `fsync`.

## Layouts

A **layout** says how to rebuild a chunked object:

- **Where:** `.qrepo/layouts/<object-id>`, the id of the logical object
  (the blob) it rebuilds.
- **Format:** UTF-8 text, one fact per line, so it is easy to inspect.

      qlayout1
      object <blob id>
      length <total body bytes>
      chunker fastcdc-1 min 65536 avg 262144 max 1048576
      <chunk-id> <raw length>
      <chunk-id> <raw length>
      ...
      check <first 16 hex of SHA-256 of all the lines above>

- **Checks:** the `check` line catches a torn or edited layout before any
  chunk is read. The real guarantee is the end-to-end one: rebuilding the
  blob streams every chunk through a hash and must end at `<blob id>`. A
  layout that lies about order, length or membership therefore fails
  verification like any corrupt chunk.
- **Lookup:** `objects/<id>` first; if absent, `layouts/<id>`. Both may exist
  during a conversion; they must decode to the same bytes, which is checked
  before the whole copy is removed.
- **Memory:** a layout for a 10 GiB file at a 256 KiB average is about 40,000
  lines, roughly 3 MB, read and processed streaming, never held whole.

Only blobs at or above a threshold, 1 MiB by default, are chunked. Notes,
trees and commits stay whole objects, so the common case stays exactly as
fast and as simple as today.

## The chunker

Content-defined chunking with FastCDC (a gear rolling hash with normalized
chunking). Boundaries depend on content, not on offsets, so an edit moves
only the boundaries near it, and every later chunk keeps its id.

- **Parameters:** minimum 64 KiB, average 256 KiB, maximum 1 MiB. The gear
  table is fixed in this spec (a 256-entry table from a stated seed), so every
  device cuts the same bytes the same way. The parameter set is named
  (`fastcdc-1`) and recorded in each layout.
- **One pass:** a commit already reads each file twice (hash where it lies,
  then copy while hashing). In qstore that second pass does everything at
  once, 64 KiB at a time in `posix.c`:
  - find boundaries
  - hash each chunk
  - hash the whole blob
  - compress each chunk
  - publish each new chunk
  - write the layout

  If the file changes during the pass, the whole-blob hash disagrees with the
  first pass; nothing reaches the layout or a tree, and the commit says to
  retry, as today.
- **Changing the chunker later** (a new parameter set `fastcdc-2`) only
  changes new layouts. Old layouts stay valid, and ids do not change, since
  chunking is representation, not identity.

## Compression

- **Algorithm:** zstd, vendored into `posix.c` (zstd has a single-file
  build). macOS ships zlib and Apple's Compression framework, but zstd is
  faster and compresses better than either, works the same on every
  platform, and has dictionaries and `--patch-from`, which later phases use.
- **Level:** 3 by default (roughly 400 to 500 MB/s per core on Apple
  silicon).
- **Per chunk, compress only if it pays:**
  - files whose magic bytes mark them as already compressed are stored raw
    without trying: JPEG, PNG, GIF, WebP, MP4/MOV, MP3/AAC, ZIP (including
    DOCX, XLSX, PPTX), gz, zst, xz, 7z;
  - otherwise compress, and keep the result only if it is at most 90% of the
    raw size.
- **Small objects** stay uncompressed in Phase 1. Phase 3 compresses them with
  a dictionary trained on the repository's own trees, commits and small
  blobs, which is where notes-heavy repositories gain most.

## Protocol 4: transfer what is missing, resumably

Protocol 3 sends a message of frames: a JSON header, then whole objects.
Protocol 4 adds chunks and layouts, and asks before it sends.

**Push**
1. `op: missing` lists the ids the push would introduce: commits, trees,
   whole objects, layouts and the chunks those layouts name. The server
   answers which it lacks.
2. `op: put` sends what is missing, in batches capped at about 64 MiB per
   request, so the one-request-at-a-time server is never held for long and
   other devices are served in between. Chunks travel in their stored
   encoding, so nothing is compressed twice. Each batch is stored and
   verified as it lands.
3. `op: push` moves HEAD, after the server has checked that the whole graph
   is present and sound, down to every chunk of every new layout, exactly as
   it checks objects today.

A push cut short loses only the batch in flight: chunks already stored stay
stored, and a retry's `op: missing` no longer lists them. **Resuming needs no
state beyond the store itself.**

**Fetch** mirrors it: the server sends commits, trees, whole objects and
layouts; the client works out which chunks it lacks and asks for them in
batches.

**Compatibility.** A protocol-3 client still pushes and fetches whole
objects. The server stores what such a client sends as whole objects (a later
`qr store convert` may chunk them), and answers its fetches by rebuilding
chunked blobs into whole objects as it streams them, checking the hash
on the way out. A protocol-4 client talking to a protocol-3 server falls back
to protocol 3. The reply header already carries `version`.

## Durability and corruption

qstore keeps format 2's rules and extends them one layer down.

- **Publication order:** chunks, then the layout, then trees, then the commit,
  then `HEAD`. A crash at any point leaves unreachable files, never a
  reachable reference to something absent.
- **Everything read is hashed:** chunks on decode, blobs as they are
  rebuilt, trees and commits as they are read, as today.
- **Verified marks** (`.qrepo/verified`) keep their meaning. A commit is
  marked once every layout below it was found present and every chunk it
  names was present and decoded to its id. Marks remain a cache with checked
  lines, rebuilt if lost.
- **`gc`:**
  1. *Mark:* walk commits to trees, to blobs, to layouts, to chunks.
  2. *Sweep:* remove unmarked chunks, layouts and objects, sparing anything
     newer than the oldest spool file or the start of a running push, so a
     transfer in flight never loses chunks it just stored.
  3. *Check:* `gc` hashes everything it keeps, as today.
- **`qr store verify`:** a scrub. It decodes and hashes every chunk, or a
  random sample with `--sample N`, without walking history, so silent disk
  corruption is found before it is needed.
- **Damage limits:**
  - a corrupt chunk spoils every file version that uses it, but only those;
  - it is detected on the first read;
  - after a fetch, any device can supply a good copy, since chunks are
    identical everywhere.

  `qr recover` learns to refetch a named chunk from the remote.
- **Safe re-encoding:** a chunk may be re-encoded (another level, a new
  dictionary) by writing the new file beside it, verifying it decodes to the
  same id, then atomically replacing the old one. The name and meaning do not
  change.

## A status cache (Phase 0, independent of the rest)

`status` and `commit` would read a local cache, `.qrepo/index`: one line per
path holding size, modification and change times (in nanoseconds), inode,
and the blob id, each line with a check like the verified marks.
- A file whose size, times and inode match its line is not hashed again.
- A line written within the same second as the file's last modification is
  not trusted, as git handles its "racy" entries, so an edit made in the
  same second as the scan is never missed.
- It is a cache, not format. Delete it and everything is hashed once.

It is worth doing first: for a large folder with nothing changed it turns
each 60-second sync tick from hashing everything into one `stat` per file.

## Where the code goes

As today: the bytes stay in C, and the decisions stay in FP-RISC.
- **`posix.c`:**
  - the chunker
  - per-chunk and whole-blob hashing
  - zstd (vendored)
  - chunk and layout publication
  - rebuilding a blob while verifying it
  - framing chunks into and out of transfer files
- **`qr.fpr`:**
  - when to chunk
  - the repository settings
  - protocol 4's operations and batching
  - graph checks, `gc` marking, verified marks
  - the CLI: `qr store stats`, `qr store convert`, `qr store verify`

No new subprocesses, and no new runtime dependencies.

## Settings

`config.json` gains `"store": 1` when a repository adopts qstore, written by
`qr store convert` or by `init` once qstore is the default. With it:
- `chunk-threshold`: 1 MiB by default
- `compress`: `auto` (default), `always` or `never`
- `level`: 3 by default

The chunker parameters are fixed per layout, not configurable per
repository, so dedup works across every repository and device.

## Phases

0. **Status cache.** Self-contained, no format change.
1. **Local qstore:**
   - chunks, layouts and the chunker
   - zstd, compressed only where it pays
   - read, write, `gc`, `verify` and `stats`
   - `qr store convert` for existing repositories: chunk large whole
     objects, verify, then remove the whole copies

   Protocol 3 still sends whole objects (the server rebuilds them).
2. **Protocol 4:**
   - missing-first negotiation
   - batched, resumable transfers
   - chunks sent in their stored encoding
   - a server that serves both versions
3. **Small objects:** a zstd dictionary trained per repository for trees,
   commits and blobs under the threshold, stored in the same chunk format
   (encoding 2), with the dictionary itself a content-addressed object.
4. **Near-duplicates and formats:**
   - **delta encoding (3):** a chunk that replaces one at the same position
     in the previous layout of the same path can be stored as
     `zstd --patch-from` against it, with a bounded chain depth
   - **ZIP-based documents (DOCX, XLSX, PPTX):** chunking the decompressed
     entries, which this design permits because it changes representation
     only

## Targets, measured as today's numbers were

| | today | Phase 1-2 target |
|---|---|---|
| a 1-byte edit to a 512 MiB file: store growth | 512 MiB | at most 1 MiB (one or two chunks) |
| the same edit: bytes pushed | 512 MiB | at most 1 MiB, plus the layout |
| text-heavy repository (notes, CSV, JSON) on disk | 1x | 3-5x smaller |
| JPEG, video, ZIP | 1x | unchanged (stored raw, no CPU spent trying) |
| a new 1 GiB file: commit | about 2 s | at most 4 s (chunk, hash, compress in one pass) |
| `status`, 10 GiB, nothing changed (with Phase 0) | about 6 s | under 0.1 s |
| peak memory, any command | under 32 MiB | unchanged |
| push cut short at 90% | starts over | resumes the last 10% |

## Tests

- **A deterministic chunker:** fixed inputs (random, all zeros, text, a file
  with an inserted byte) produce fixed boundary lists, checked into the
  tests, so every device and every build cuts identically.
- **Corruption:**
  - a flipped byte in a chunk, a truncated chunk, a wrong `raw length`, a
    layout with chunks swapped, a missing chunk: each is detected on read, by
    `verify`, and by the server's graph check before HEAD moves
  - a lying server's chunk is refused
- **Crashes:** the existing fault-injection build (`QREPO_TEST_FAULTS`) kills
  the process at each publication step of a chunked commit and a resumed
  push; HEAD is always a complete old or new checkpoint.
- **Decoder robustness:** fuzz the chunk header and payload, including
  decompression bombs and lengths that don't match.
- **Compatibility:** a protocol-3 client against a protocol-4 server and the
  reverse; a format 2 repository before and after `qr store convert`, which
  keeps every commit id.
- **The numbers above:** the 512 MiB measurement of 2026-10-31 rerun as a
  benchmark.

## Open questions

1. **Chunk sizes.** A 256 KiB average suits edited PDFs and spreadsheets.
   For a repository of mostly video, 1 MiB would mean fewer files. One fixed
   set keeps dedup universal. Measure on real folders before Phase 1 is
   frozen.
2. **Converting the server store.** The mini's store would be converted once
   all devices run Phase 2, or left to convert lazily as new pushes arrive.
3. **Disk on the server during a push:** batches bound it to about 64 MiB of
   spool at a time, instead of the whole push.
4. **Vendoring zstd:** about 1 MB of C to review and keep up to date. The
   alternative is the platforms' zlib, which loses about a third of the
   ratio and the dictionary and delta features.
5. **Garbage collection with several devices:** a chunk unreachable on the
   server may still be wanted by a device mid-fetch. The grace rule above
   covers one server; it needs a test with two devices fetching while the
   server runs `gc`.
